# SDK boundary for multiple GitLab instances and accounts

Research snapshot: 24 September 2026. Evidence below refers to the pinned OpenChamber source revision [`19112c5`](https://github.com/openchamber/openchamber/tree/19112c58edc71b7c5f36bca766a83c73710204b2), not an unversioned future API. A **GitLab connection** is one user's authorization for one GitLab account on GitLab.com or one self-managed instance. This report establishes constraints; it does not decide the product design.

## Documented and verified boundary

- The manifest declares one integration, with exactly one of `token`, `oauth`, or `host`; token and OAuth declarations each contain one fixed `apiOrigin`. The public integration card exposes that origin and one authentication mode. [Pinned SDK manifest](https://github.com/openchamber/openchamber/blob/19112c58edc71b7c5f36bca766a83c73710204b2/packages/sdk/src/manifest.ts#L151-L254) · [SDK accounts documentation](https://docs.openchamber.dev/sdk/#accounts-and-network)
- `host.request({ method, path, ... })` accepts a path, not a caller-selected host. Server-side URL joining rejects a URL outside the declared origin, and the server adds credentials for that extension. It does not expose the token to the panel. This cannot dynamically select another GitLab instance's API origin. [Pinned request implementation](https://github.com/openchamber/openchamber/blob/19112c58edc71b7c5f36bca766a83c73710204b2/packages/web/server/lib/guests/request.js#L14-L81) · [Host API](https://docs.openchamber.dev/sdk/host/#request)
- Stored authorization and settings are keyed by extension (guest/panel) ID, not by an arbitrary number of account profiles. OAuth state is not a documented multi-account selection interface. The stored target includes the API origin and, for OAuth, authorization/token URLs, so changed endpoints do not inherit old credentials. The SDK contribution's `settings` fields are plain text, **not** extra secure token slots or a dynamic-origin authorization grant. [Pinned auth store](https://github.com/openchamber/openchamber/blob/19112c58edc71b7c5f36bca766a83c73710204b2/packages/web/server/lib/guests/auth-store.js) · [SDK accounts documentation](https://docs.openchamber.dev/sdk/#accounts-and-network) · [Upstream extension implementation PR](https://github.com/openchamber/openchamber/pull/3460)

## Paths and their limits

| Path | Classification | Consequence |
| --- | --- | --- |
| One extension with a fixed GitLab origin and one connected account | **Documented host API** | Uses the host's credential isolation and approval; cannot switch origins or maintain multiple GitLab connections in that one integration. |
| Separately packaged copies, each with a distinct panel ID and a fixed API origin | **Source-supported inference; not documented as multi-instance support** | The installer rejects an already-installed package root and a duplicate ID. Distinct copies might isolate connections, but require independently built/configured packages and do not make a single panel dynamically route to multiple origins. Installation, upgrades, UX and OAuth behavior need a real compatibility test. [Pinned installer](https://github.com/openchamber/openchamber/blob/19112c58edc71b7c5f36bca766a83c73710204b2/packages/web/server/lib/guests/install.js#L39-L69) |
| Native host profile-ID API for multiple approved origins and credentials | **Upstream enhancement suggestion, not shipped contract** | A host-owned profile selector and per-profile origin/credential/approval checks could retain isolation without exposing tokens. Exact API, migration, and timing require upstream agreement and testing. |
| Extension-operated proxy or local service | **Custom workaround, not equivalent SDK isolation** | A proxy adds credential custody, origin validation, deployment and operational burden. A host service runs with the user's full rights outside the iframe sandbox; it is not a low-risk shortcut. [SDK service documentation](https://docs.openchamber.dev/sdk/#manifest) · [Extensions permissions](https://docs.openchamber.dev/extensions/#what-an-extension-may-do) |

Changing the manifest origin is **not** a safe account switch: the approval target changes and existing credentials are bound to their original target. Verify update/reapproval behavior on the selected host version; the [upstream implementation PR](https://github.com/openchamber/openchamber/pull/3460) discusses this boundary. The [open first-party GitLab PR #3457](https://github.com/openchamber/openchamber/pull/3457) may change native behavior but is **not** a released SDK contract. Unresolved: minimum OpenChamber version, self-managed instance authentication variations, repeated package installations in production, and whether upstream will support host-managed multiple GitLab profiles. No design ticket is resolved here.
