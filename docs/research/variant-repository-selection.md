# Repository selection with two GitLab extension variants

Research snapshot: 24 September 2026. Source observations are pinned to OpenChamber [`19112c5` (v2.0.0)](https://github.com/openchamber/openchamber/tree/19112c58edc71b7c5f36bca766a83c73710204b2). A **local repository** is the directory open in OpenChamber; a **GitLab connection** authorizes one account on GitLab.com or a self-managed instance. These findings describe the boundary, not a product choice.

## Confirmed host behavior

- Two distinct package roots with **different panel IDs** can be installed without triggering the installer's duplicate-root or `id-taken` rejection. The panel ID must be unique. This is source-level evidence for coexistence, **not** a documented per-repository variant selector. [SDK manifest](https://docs.openchamber.dev/sdk/#manifest) · [Pinned installer](https://github.com/openchamber/openchamber/blob/19112c58edc71b7c5f36bca766a83c73710204b2/packages/web/server/lib/guests/install.js#L39-L69)
- Credentials/settings are stored under the extension ID, persistent extension data has a separate file per ID, and `host.request` uses that extension's declared `apiOrigin` and credential. One variant does not get the other's token through the documented host request path. Changing an origin is not a safe way to switch accounts. [Pinned auth store](https://github.com/openchamber/openchamber/blob/19112c58edc71b7c5f36bca766a83c73710204b2/packages/web/server/lib/guests/auth-store.js) · [Pinned storage](https://github.com/openchamber/openchamber/blob/19112c58edc71b7c5f36bca766a83c73710204b2/packages/web/server/lib/guests/storage.js) · [Pinned request proxy](https://github.com/openchamber/openchamber/blob/19112c58edc71b7c5f36bca766a83c73710204b2/packages/web/server/lib/guests/request.js#L64-L81)
- The initial host context includes `directory`, not a local-repository/project ID or detected GitLab remote. `listProjects` is a separate API that needs the `sessions` capability. Active extension rail surfaces use `plugin:<panel-id>` modes, and context-panel UI state is keyed by directory. A user can manually open the intended variant in a local repository; remembered panel UI state is **not** an authoritative GitLab connection mapping or a guarantee that the matching variant opens automatically. [Pinned host context](https://github.com/openchamber/openchamber/blob/19112c58edc71b7c5f36bca766a83c73710204b2/packages/sdk/src/contract.ts#L186-L200) · [Host session API](https://docs.openchamber.dev/sdk/host/#projects-worktrees-and-live-sessions) · [Pinned surfaces](https://github.com/openchamber/openchamber/blob/19112c58edc71b7c5f36bca766a83c73710204b2/packages/ui/src/lib/guests/surfaces.ts#L32-L52) · [Pinned panel state](https://github.com/openchamber/openchamber/blob/19112c58edc71b7c5f36bca766a83c73710204b2/packages/ui/src/stores/useUIStore.ts#L1448-L1462)
- `attach`, `startSession`, and `sessionLink` enforce the calling variant's `providerId`; attached item provenance is not a remote-origin or local-repository correctness check. A wrong variant can present the wrong account's issues for the currently open directory unless product logic prevents it. Installed variants can each contribute globally visible attach entries/actions rather than having the host hide the wrong variant for the active local repository. [Pinned panel bridge](https://github.com/openchamber/openchamber/blob/19112c58edc71b7c5f36bca766a83c73710204b2/packages/ui/src/components/layout/PluginPane.tsx#L104-L111) · [SDK contributions](https://docs.openchamber.dev/sdk/#actions-commands-and-the-badge) · [Host item API](https://docs.openchamber.dev/sdk/host/#attach-startsession-and-sessionlink)

## Unsupported assumptions and lifecycle caveats

The pinned panel bridge passes `openSurface` to the UI's directory-scoped surface opener. `openSurface("plugin:<other-id>")` therefore **appears possible in current source**, but the public SDK does not promise cross-extension targets or stable modes; do not rely on it as a supported switch mechanism. There is likewise no documented host operation to match a GitLab remote to a variant or dispatch the other variant's privileged actions. [Pinned panel bridge](https://github.com/openchamber/openchamber/blob/19112c58edc71b7c5f36bca766a83c73710204b2/packages/ui/src/components/layout/PluginPane.tsx#L412-L415) · [Host API: openSurface](https://docs.openchamber.dev/sdk/host/#methods)

A folder install runs in place and is updated manually; ZIP and URL installs are copied, while Git URL installs support update checks. Stable, distinct IDs and independently maintained packages would be needed for two fixed-origin variants. Revalidate coexistence, panel state, and UI entry placement against the actual deployed OpenChamber version; pinned source is not a cross-version guarantee. [Extensions: install and update](https://docs.openchamber.dev/extensions/#install-one) · [Extensions: update](https://docs.openchamber.dev/extensions/#update)

## Questions for [D3: per-repository connection and GitLab project matching](https://github.com/ShadyF/openchamber-extension-gitlab/issues/7)

1. What explicit mapping, if any, should associate a local repository with a GitLab connection, and who confirms a changed/missing remote?
2. How should a wrong-account variant behave in panel, composer attach picker, and actions when multiple local repositories or GitLab instances are open?
3. Is manual variant choice acceptable, or does the desired experience require an upstream selector/API instead of unpromised cross-variant dispatch?
4. What install/update and supported-version policy can maintain two independently identified variants without accidental credential or UI confusion?
