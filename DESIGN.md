# GitLab panel UX contract

This is a **target design** with a separate current-source boundary below, not proof that every pictured workflow has shipped. The approved visual and interaction reference is [standalone prototype A](.impeccable/prototypes/gitlab-workspace.html?variant=A). Its host frame, people, projects, branches, issues, merge requests, status, and action feedback are fictional sample data; its lab state selectors, variant switcher, and preview-only controls are not product UI. Use it to guide the panel, not as evidence of API integration.

## Present implementation and scope

Current source includes connected Setup, project association, and an extracted associated-project workspace in `src/workspace.ts` with a compact repository strip, GitLab work hierarchy, real project-scoped merge-request search with bounded pagination, full-width MR detail, visible Back navigation, verified session-linked issue and MR focus, related-MR discovery after a verified issue link across bounded pages, and issue-linked worktree creation for registered repositories. MR detail presents read-only **Overview**, **Pipelines & jobs**, and **Discussions** sections. Overview shows title, state, description, branches, and URL. Pipeline and discussion content loads on demand with bounded pagination; jobs use the pipeline's returned project ID. The activity controller authorizes loads only for the matching verified MR visible in the workspace. Sections independently represent empty, unavailable, error, and truncated results and offer retry where applicable. One visible opened related MR is focused as related, not explicitly linked; ambiguity, incomplete pages, and unavailable results fall back to the issue. The Issues queue shows real Open/Issue/date metadata; no fake Filter or Assigned-to-you controls are present. An unregistered directory can choose a project for this panel session and browse issues but cannot create a worktree. One persistent recovery record blocks repeat creation after an uncertain or partial result until checked or manually released. Phase-2 source validation passes 206 tests across 12 files, typecheck, standard bundle, package validation, and `git diff --check`. ## Target panel behavior

- Keep the GitLab extension inside OpenChamber's right-side panel. Follow the host's theme, spacing, interaction patterns, and SDK UI controls where applicable; do not give it a separate product identity. Identify the associated GitLab project and local repository in a compact strip, with a secondary way to change the association.
- Treat an absent GitLab connection and an absent project association as **Setup conditions**, not permanent product tabs. Direct connection setup to OpenChamber **Settings → Integrations**, where credentials remain protected. Let the user search and choose a visible GitLab project when association is missing; avoid showing an issue or merge-request list without a usable association.
- Without a verified session context item, show the associated GitLab project's work in a single-column list with **Issues** and **Merge requests** as work-type choices. Selecting a row replaces the list with that item's full-width detail; **Back to list** restores the list. Never place a second queue beside the detail in the narrow panel.
- From an issue detail, **Open in new worktree** uses OpenChamber's SDK session-start flow to create and open a worktree session with that issue attached. It does not send an opening message or start the agent automatically. OpenChamber SDK v2.0.0 does not let extensions register or invoke Magic Prompts, and the built-in PR Review prompt is specific to GitHub. Do not present a simulated action as a working one.
- Persist one unresolved worktree-creation attempt before dispatch. A timeout or partial result must not enable another creation; preserve recovery details across panel reloads, and use the host's existing-session navigation only after a confirmed creation result. The host supplies no idempotency key, so do not claim exactly-once creation.
- When the active session is **verified** as linked to an issue, prioritize that issue's focused detail instead of the project list. For a future merge-request creation flow, hand off to OpenChamber's native Git UI to push the session branch. Only once GitLab confirms a remote source branch should its merge-request form become available. GitLab needs a pushed source branch; OpenChamber SDK v2.0.0 cannot enumerate local Git branches or push them, and its built-in GitHub pull-request panel cannot be embedded as this extension's GitLab UI. Do not infer a push from a local branch name or show an enabled creation path before remote verification.
- An explicit **verified session MR link takes precedence** in current source and shows its real Overview, Pipelines & jobs, and Discussions sections. Pipeline, job, and discussion views are read-only; there are no merge-request actions, job logs, or artifacts. When an issue-only linked session is verified, current source checks GitLab's issue `related_merge_requests` endpoint across bounded pages. If there is exactly **one visible opened MR**, it focuses that MR as **related**, not explicitly linked: a mention in an issue or note can qualify. With zero or multiple matches, incomplete pages, or permission/API errors, the issue remains in focus. Inaccessible MRs may exist, so results do not prove their absence. Do not infer a link from branch names, titles, or sample data.

Prototype controls such as filters, AI drafting, optional context, merge buttons, and demo navigation are illustrative, **not committed capabilities**. The prototype remains a target visual reference; current source previews—not the prototype—demonstrate the implemented read-only MR sections. Any later implementation of actions must resolve permissions, live GitLab state, failures, and the exact verification path before enabling them.
