# Release and dependency automation research

This explanation records supported options for releasing the OpenChamber GitLab extension after changes reach `main`. It distinguishes documented behavior from choices the project still needs to make. Research checked 2026-09-24.

## Verified behavior

- **Release calculation:** semantic-release's default Angular commit analyzer makes `feat` a minor release, `fix` and `perf` patch releases, and a `BREAKING CHANGE` major release. Other commits need not create a release. Version-bump commits are unnecessary: semantic-release determines the next version from commits and existing tags. Its first release is `1.0.0` if no prior release tag exists. [semantic-release FAQ](https://semantic-release.org/support/faq/) · [configuration](https://semantic-release.org/usage/configuration/)
- **GitHub Actions:** the documented recipe runs on pushes to the release branch, checks out full history (`fetch-depth: 0`), runs tests, and then runs semantic-release. Publishing a GitHub Release requires `contents: write`; limit this permission to the publishing job. Workflows triggered by a push made with the repository's `GITHUB_TOKEN` do not normally start further workflow runs, preventing release-commit loops. A dry run checks release calculation without publishing, but cannot fully validate write permissions or actual publication. [semantic-release GitHub Actions recipe](https://semantic-release.org/recipes/ci-configurations/github-actions/) · [GitHub `GITHUB_TOKEN` behavior](https://docs.github.com/en/actions/concepts/security/github_token/) · [semantic-release configuration](https://semantic-release.org/usage/configuration/)
- **Dependency updates:** the hosted Renovate GitHub App supports repository onboarding and a standard preset; its GitHub Actions manager detects and updates action references, including pinned action versions. This does not require maintaining a custom dependency bot. [Renovate onboarding](https://docs.renovatebot.com/getting-started/installing-onboarding/) · [GitHub Actions manager](https://docs.renovatebot.com/modules/manager/github-actions/)
- **Distribution:** OpenChamber documents third-party extension installation from a Git URL, ZIP, or local folder. A Git URL can target a `#tag` or `#branch` and supports updates. Extensions must ship bundled IIFE JavaScript. No extension marketplace or registry distribution path is documented here; do not substitute VSIX, npm, or OpenCode-plugin release assumptions. [OpenChamber install options](https://docs.openchamber.dev/extensions/#install-one) · [OpenChamber SDK](https://docs.openchamber.dev/sdk/)

## Recommended implementation and open decisions

Use a protected `main` branch, require the test workflow before merging, and run semantic-release on pushes to `main` after tests pass. Grant only the publishing job `contents: write` for GitHub Releases; check out complete Git history and preserve release tags. Install the hosted Renovate App with its standard preset and pin/update GitHub Actions through Renovate. Publish a bundled IIFE extension through a versioned Git tag URL or attach a built ZIP to the GitHub Release so users can follow OpenChamber's documented install flow.

**Decision for #8:** “release when commits land on `main`” means *qualifying Angular commits* create releases under semantic-release defaults; documentation-only or other nonqualifying commits do not. If every push must publish, explicitly choose and design a different release rule rather than assuming semantic-release will do so. Before enabling automation, confirm the intended initial version and any pre-existing tags, branch/tag protection rules, required-check names, and which install artifact or Git URL users should receive. This report does not configure automation or claim an artifact is already published.
