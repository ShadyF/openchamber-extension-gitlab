# GitLab API and self-managed compatibility research

Research for [issue #3](https://github.com/ShadyF/openchamber-extension-gitlab/issues/3). This is a capability and constraint survey, not a selected integration design. A **local repository** is the workspace opened in OpenChamber; a **GitLab project** is the repository and associated issues and merge requests on an instance; a **GitLab connection** relates one user account to one GitLab.com or self-managed instance. Documentation checked September 2026.

## REST resources and identifiers

- The instance's REST API is rooted at `https://<host>/api/v4`. Endpoints accepting a project `:id` accept its numeric ID or URL-encoded namespace/project path (for example, `group%2Frepo`). Do not confuse an API-wide `id` with a project-local `iid`. Default offset pagination uses `page` and `per_page`; follow pagination links rather than assuming one page contains every result. [REST API](https://docs.gitlab.com/api/rest/)
- An authenticated `GET /user` returns the current account. `GET /projects/:id` retrieves a visible GitLab project; project results include `ssh_url_to_repo`, `http_url_to_repo`, `visibility`, and, for forks, upstream information such as `forked_from_project`. These fields provide candidates for a later local-repository association policy, **not** a canonical matching algorithm. Project visibility and the current account's permissions limit what lookup can return. [Users API](https://docs.gitlab.com/api/users/) · [Projects API](https://docs.gitlab.com/api/projects/)
- `GET /projects/:id/issues` and `GET /projects/:id/issues/:issue_iid` operate in project context. The global `GET /issues` has its own scope defaults; `scope=all` requests accessible issues rather than all issues on the instance. An issue's `iid` is local to the GitLab project; its `references` include short (`#6`) and fully qualified (`group/repo#6`) forms. [Issues API](https://docs.gitlab.com/api/issues/)
- `GET /projects/:id/merge_requests` and `GET /projects/:id/merge_requests/:merge_request_iid` similarly use a project-local IID. Merge request references include short (`!123`) and fully qualified (`group/repo!123`) forms. For links spanning projects, retain the instance and project context; an IID alone is not globally unique. [Merge requests API](https://docs.gitlab.com/api/merge_requests/)
- GitLab's Markdown renderer accepts a `project` parameter to give GitLab Flavored Markdown references project context. This is a rendering capability, not a rule for linking local repositories to projects. [Markdown API](https://docs.gitlab.com/api/markdown/)

## Authentication and permissions

- GitLab documents authorization-code OAuth with PKCE using instance-local `/oauth/authorize` and `/oauth/token` endpoints. PKCE uses a verifier/challenge and does not require a client secret; validate `state` and use HTTPS in production. GitLab supports user-owned, group-owned, and self-managed instance-wide application registration, but availability and approval of an application on a particular instance remain operational questions. [OAuth identity provider API](https://docs.gitlab.com/api/oauth2/) · [Configure GitLab as OAuth provider](https://docs.gitlab.com/integration/oauth_provider/)
- OAuth access tokens are sent as `Authorization: Bearer …`; personal and project access tokens can use `PRIVATE-TOKEN: …`. OAuth refresh exchanges rotate tokens, so a client must not assume an old refresh token remains usable. `read_api` provides API read access; `api` provides API read/write access. Choose scopes against actual required actions, not merely the existence of issue and merge request read endpoints. [REST authentication](https://docs.gitlab.com/api/rest/authentication/) · [OAuth identity provider API](https://docs.gitlab.com/api/oauth2/) · [Configure GitLab as OAuth provider](https://docs.gitlab.com/integration/oauth_provider/)
- Personal access tokens are an alternative to OAuth, subject to configured scope, expiration, and account permissions. Project access tokens represent project bot users and are not interchangeable with a user's account-wide GitLab connection; on GitLab.com, creating them requires Premium or Ultimate (with a trial limit). Neither a token nor a broad scope overrides private-project authorization. [Personal access tokens](https://docs.gitlab.com/user/profile/personal_access_tokens/) · [Project access tokens](https://docs.gitlab.com/user/project/settings/project_access_tokens/) · [Projects API](https://docs.gitlab.com/api/projects/)

## Self-managed compatibility boundary

- The Metadata API documents instance version endpoints (`GET /metadata` and `GET /version`). Their presence can inform a compatibility check but cannot establish feature parity across versions, editions, admin configuration, or permissions. The current referenced page does not state an introduction version; the reported GitLab 17.6 introduction of `/metadata` needs confirmation against release history before using it as a minimum-version gate. [Metadata API](https://docs.gitlab.com/api/metadata/)
- GitLab documents TLS 1.2 and 1.3 support; older TLS/SSL protocols are unsupported. These GitLab server docs do **not** establish that any prospective extension SDK accepts private certificate authorities, insecure certificates, arbitrary self-managed hosts, or every GitLab version. Do not promise any of those client behaviors without separate client-side verification. [TLS support](https://docs.gitlab.com/security/tls_support/) · [REST API](https://docs.gitlab.com/api/rest/)
- API access is permission-scoped and may be restricted by private visibility, instance configuration, and token scope. A generic `/api/v4` shape and OAuth endpoints are evidence of supported GitLab mechanisms, not proof that a particular self-managed deployment is reachable or functionally identical to GitLab.com. [Projects API](https://docs.gitlab.com/api/projects/) · [REST authentication](https://docs.gitlab.com/api/rest/authentication/)
