# OpenChamber capabilities relevant to a GitLab extension

Research snapshot: 24 September 2026. This is a capability inventory, not a promise that a GitLab extension will match the built-in GitHub or Linear integrations. OpenChamber's latest release at this snapshot was [v2.0.0](https://github.com/openchamber/openchamber/releases/tag/v2.0.0); confirm behavior against the version actually deployed.

## Confirmed extension contracts

- An extension ships a `package.json` manifest and a prebuilt, classic-script panel in a sandboxed iframe. `apiVersion` is `1`; `engines.openchamber` can reject older hosts. Panels run in **web and desktop**, not VS Code or mobile. Manifest contributions include a rail panel, optional full-screen page, composer attach picker, message/session actions, slash commands, badges, and tool-call presentation. Permissions are approved at installation and revisited when an update expands them. [SDK overview](https://docs.openchamber.dev/sdk/) · [Extensions](https://docs.openchamber.dev/extensions/)
- `connectHost()` exposes current local repository directory, session, item, connection and settings snapshots. `attach`, `sessionLink`, and `startSession` take an item whose `kind` is `issue` or `pull` (use `pull` for a GitLab merge request). `startSession` can target a registered project/worktree and reports partial creation outcomes; `compose` and `prompt` prepare or send text. Session, file and prompt operations require their respective permissions. The host stores one composer chip at a time; attachment `data` returns to the extension but is **not** model context, whereas `text` can supply model context. [Host API: attach and sessions](https://docs.openchamber.dev/sdk/host/#attach-startsession-and-sessionlink) · [Host API: methods](https://docs.openchamber.dev/sdk/host/#methods)
- An extension integration can request a user-entered token or OAuth connection. Its iframe cannot access the network directly: `host.request` proxies through the declared `apiOrigin` with server-held credentials, and its response body is text. The documented `host: { provider: "linear" }` reuse has a narrow built-in issue-get route; this is **not** a general-purpose route to GitHub, Linear, or GitLab built-in APIs. A GitLab instance's API origin therefore needs its own connection design; self-managed instance selection and authentication details remain open. [SDK: accounts and network](https://docs.openchamber.dev/sdk/#accounts-and-network) · [Host API: request](https://docs.openchamber.dev/sdk/host/#request)
- Local folders, local ZIPs, and Git/ZIP URLs are supported installation inputs. Ship compiled files: OpenChamber does not build sources on install. Git URL installs support version-based update checks; folders and ZIPs require manual replacement. Private SSH Git installs depend on the selected OpenChamber server's Git identity, not automatically the desktop's key. [SDK: install](https://docs.openchamber.dev/sdk/#install-it-while-you-work) · [Extensions: private repositories and updates](https://docs.openchamber.dev/extensions/#private-repositories-and-git-identities)

## Built-in workflows are precedents, not extension APIs

- GitHub's native connection supports multiple accounts and device authorization (with `gh` fallback). Native issue/PR pickers attach an issue with comments or a PR with optional diff, and can start a worktree session; the Git view creates, updates, marks ready, and merges PRs. These are **built-in UI/server flows**; the SDK provides item and session primitives, not a documented GitHub picker/PR-management API for extensions. [GitHub guide](https://docs.openchamber.dev/github/) · [GitHub server module](https://github.com/openchamber/openchamber/blob/main/packages/web/server/lib/github/DOCUMENTATION.md) · [issue picker](https://github.com/openchamber/openchamber/blob/main/packages/ui/src/components/session/GitHubIssuePickerDialog.tsx) · [PR picker](https://github.com/openchamber/openchamber/blob/main/packages/ui/src/components/session/GitHubPrPickerDialog.tsx)
- Linear's native server supports multiple workspaces, issue lookup/comments/status, team-to-local-repository mapping and worktree sessions. Optional started/completed/failure issue comments require explicit opt-in and a publicly reachable session URL. The built-in picker is native UI; an extension cannot assume access to those server routes beyond the documented narrow Linear host exception above. [Linear server module](https://github.com/openchamber/openchamber/blob/main/packages/web/server/lib/linear/DOCUMENTATION.md) · [Linear picker](https://github.com/openchamber/openchamber/blob/main/packages/ui/src/components/session/LinearIssuePickerDialog.tsx) · [Host API: request](https://docs.openchamber.dev/sdk/host/#request)
- The [Docker extension manifest](https://github.com/openchamber/openchamber-extension-docker/blob/main/package.json) declares a host-runtime service with permission to execute `docker`. This demonstrates an **optional, privileged** escape hatch for host-only resources, not evidence that GitLab needs one. Prefer the documented integration/network path if it meets the GitLab use case. Its `engines.openchamber: >=1.22.0` differs from the SDK manifest example's `>=1.24.0`; neither example alone establishes a tested minimum for this project. [SDK: service and version](https://docs.openchamber.dev/sdk/#manifest)

## Inferences and unresolved decisions

A GitLab panel can plausibly list issues/merge requests through `host.request`, attach them as `issue`/`pull`, and start sessions with context; **the actual GitLab API operations, permissions, instance policy, and UI behavior must be designed and tested**. No cited SDK contract promises native GitLab project mapping, merge-request checkout/diff, review, merge, or automatic status comments. Treat those as separate feature choices rather than inherited parity.

Follow-up decisions belong to tickets **#5–#8**: GitLab connection/authentication and self-managed origins; issue/MR context and local-repository mapping; worktree/merge-request operations; and distribution/version compatibility. Validate each against its own scope before implementation.
